## Problem

Submission adapters construct persistence and execution details themselves.
The admin API and GitHub-comment path duplicate validation payload checks,
hashing, axes, provenance, and worker constraints. Benchmark, Slack, trigger,
cache-warm, and prepared fleet paths each use separate creation methods.
Additional GitHub, watched-ref, and Slack validation producers would multiply
these correctness-sensitive paths.

The hardest shape is a benchmark submission: one aggregate owns multiple specs
and ordered steps, while only its first runnable job is initially materialized.
Designing the kernel around singleton validation first could produce an
interface that fights existing group-level idempotency, reporting, and lazy
workflow advancement.

## Terminology and Ownership

```text
surface adapter
  authenticate + authorize + resolve mutable ref to immutable commit
        |
        v
task-specific planner
  validated BenchmarkPlan / BuildOnlyPlan / ValidationPlan
        |
        v
task-submission kernel
  submission identity + frozen plan + provenance + idempotency
  + initial prepared job(s), committed atomically
        |
        v
queued immutable demand
        |
worker poll
        v
pull scheduler
  matches required capability/constraints and records assignment
        |
        v
fleet coordinator
  offer/accept + attempt/lease/fence + events + cleanup
```

- A **submission** is the durable aggregate root for one user/system request.
- A **task plan** is its immutable, task-specific topology and parameters.
- A **job** is one concrete schedulable unit materialized from that plan.
- An **attempt** is one fenced worker execution of a job.

Submission does not inspect live sessions, reserve resources, select a worker,
push work, or wait for execution. Claim/offer observes only a concrete job and
never parses, resolves defaults for, expands, or replans a submission.

## Design Rules

- **Submission, scheduling, and coordination are separate.** Submission records
  immutable demand. The existing worker-initiated pull transaction selects an
  eligible job. The existing fleet state machine owns attempts and execution.
- **One submission identity everywhere.** Reporting, provenance, idempotency,
  lifecycle lineage, and receipts identify the aggregate, not its first job.
- **Benchmark first.** The first kernel writer supports the most complex
  existing multi-spec and/or sequential-run benchmark shape. Singleton
  validation follows only after that contract passes.
- **Plan completely; materialize only ready work.** Persist every spec and
  ordered step at submission. Create only initial ready jobs; the coordinator
  materializes later sequential jobs from the frozen plan.
- **Closed task plans, not plugins.** Use an exhaustive task-plan enum with
  benchmark/build-only/validation planners. Comparisons, repetitions,
  validation ranges, and shard policy remain task-specific.
- **Idempotency belongs to the aggregate.** A namespaced producer key maps to a
  submission and versioned request digest. Same key/digest returns the original
  receipt; same key/different digest fails closed.
- **Provenance belongs to the aggregate.** GitHub delivery/user/PR/comment and
  Slack request/report identities are persisted with the submission.
- **Constraints are not assignments.** Immutable required worker/profile
  constraints are distinct from scheduler-owned assigned worker/profile state.
- **No live-worker dependency.** Valid demand persists while no compatible
  worker is connected.
- **Adapters stay thin.** Surfaces authorize, resolve external identity, and
  translate typed input. They do not construct persistence rows, payload
  digests, or source-link SQL.
- **One kernel cutover.** Once all producers use the kernel, remove or privatize
  superseded broad writers; no permanent old/new creation paths remain.

## Target Contract

The exact Rust layout is implementation-owned, but the boundary must express:

```rust
struct SubmissionCommand {
    source: ResolvedSource,
    actor: SubmissionActor,
    producer_key: ProducerKey,
    constraints: SchedulingConstraints,
    task: TaskPlan,
}

enum TaskPlan {
    Benchmark(BenchmarkPlan),
    BuildOnly(BuildOnlyPlan),
    BlockValidation(ValidationPlan),
}

struct SubmissionReceipt {
    submission_id: SubmissionId,
    disposition: SubmissionDisposition, // Created | AlreadySubmitted
    initial_job_ids: Vec<JobId>,
}
```

The command contains no live session, lease, selected worker, backend path, or
libvirt setting. Task planning produces a versioned canonical request encoding.
Its digest covers every input that changes executable demand: resolved commits,
effective arguments, variants/repetitions, validation range/shard policy, and
scheduling constraints. Presentation-only metadata is excluded.

Idempotency maps to `SubmissionId`, not the first job. A receipt therefore
remains stable after that job terminates or later jobs are materialized.

## Persistence Changes

Against v27.1's renamed schema, v27.2 intentionally:

- adds an all-or-none submission contract version and request digest;
- adds namespaced aggregate idempotency mapped to `task_submission_id`;
- moves GitHub producer/user/PR/comment relationships to the submission while
  preserving job-event history;
- moves Slack request/report identity required for atomic creation to the
  submission;
- replaces overloaded `worker_id`/`measurement_profile` state with immutable
  `required_worker_id`/`required_measurement_profile` and scheduler-owned
  `assigned_worker_id`/`assigned_measurement_profile`;
- gives each concrete job an immutable required worker capability so scheduling
  no longer derives it through a task-kind `CASE`; and
- asserts the unused legacy `host_key` is empty before dropping it.

For existing submissions, conservatively copy non-null legacy worker/profile
values into both required and assigned fields. This preserves every prior pin
or affinity because the old schema cannot prove which role first wrote it. New
submissions begin with assigned fields empty.

Do not fabricate canonical request digests for history lacking enough frozen
input. Version/digest may both be null only for migrated pre-v27.2 submissions;
new kernel writes require both. Existing producer links still reconcile retries
to historical submissions. Restart/replace may later fail explicitly when a
legacy plan cannot be reconstructed losslessly.

## Phases

### Phase 1: Kernel Contract and Benchmark-First Characterization

**Goal:** Prove the aggregate envelope against the hardest task shape.

**Scope:**

- Inventory every production producer and classify surface-owned resolution
  versus planner/kernel derivation.
- Define command, plans, producer key/digest, receipt, and a narrow persistence
  port.
- Capture multi-spec ordering, repetitions, calibration, one initial runnable
  job, lazy continuation, artifact/report identity, and rollback in Postgres
  tests.
- Add failing tests for fresh submission, exact replay, conflicting replay, and
  failure at each transaction boundary.

**Acceptance & Validation:**

- The contract represents the largest benchmark submission without a
  job-or-group return union.
- Every mutable/default-derived executable input is frozen before persistence.
- Claim/offer accepts only concrete jobs and contains no submission planner.
- Singleton validation is not used to narrow the contract.

### Phase 2: Aggregate Persistence and Benchmark-First Writer

**Goal:** Implement aggregate idempotency/provenance and the hardest writer
before singleton support.

**Scope:**

- Add the intentional v27.2 persistence changes above in one transactional
  migration.
- Implement the Postgres kernel transaction for multi-spec/repeated benchmark
  submissions.
- Persist submission, complete plan, provenance/idempotency, and only initial
  ready jobs atomically.
- Return the canonical receipt for created and replay outcomes.

**Acceptance & Validation:**

- Same key/digest returns the same submission after the initial job terminates;
  same key/different digest returns a typed conflict.
- Simultaneous first submissions elect one canonical aggregate.
- Injected failures leave no partial submission, plan, job, provenance, or key.
- Sequential continuation still materializes later jobs only after predecessor
  completion and never during claim.
- Legacy constraint/digest backfill follows the documented conservative rules.

### Phase 3: Benchmark and Build-Only Producer Cutover

**Goal:** Make the kernel the sole creation path for existing benchmark-shaped
work.

**Scope:**

- Route GitHub comments, branch/tag triggers, Slack ad-hoc requests, cache
  warming/build-only, and admin producers through task planners and the kernel.
- Freeze mutable refs and effective arguments before submission.
- Preserve plan topology, calibration, carried artifacts, comparisons, Slack
  report identity, and queued-event content.
- Preserve lazy coordinator materialization from the frozen plan.

**Acceptance & Validation:**

- Equivalent requests across surfaces produce byte-equivalent executable plans
  and source-appropriate provenance.
- Existing behavior/report fixtures remain unchanged except for v27.1's
  intentional internal vocabulary.
- No producer constructs persisted submission/spec rows, `NewJob`, execution
  digests, or source-link SQL.
- Scheduler/coordinator tests prove unchanged ordering, affinity, attempts,
  leases, fencing, cancellation, and cleanup.

### Phase 4: Block-Validation Singleton Cutover

**Goal:** Apply the proven aggregate contract to the simpler singleton.

**Scope:**

- Add the validation planner and route the admin API plus existing
  `/validate-blocks` producer through the kernel.
- Freeze epoch, inclusive range, shards, concurrency, timeout, commit,
  capability, and authorized constraints in the request digest.
- Stop requiring a live/specific worker for ordinary validation submissions.
- Keep explicit worker/profile constraints operator-only.

**Acceptance & Validation:**

- Admin and GitHub forms of the same request produce byte-equivalent immutable
  demand and the same receipt under replay.
- Submission succeeds with no connected worker and is later offered only to a
  compatible polling worker.
- Unauthorized/malformed constraints fail before persistence; a valid
  constraint with no eligible worker remains queued unchanged.
- No worker-local path, libvirt setting, or chainstate-origin name enters the
  contract.

### Phase 5: Boundary Enforcement and Dead-Path Removal

**Goal:** Make bypassing the kernel difficult.

**Scope:**

- Remove or privatize broad linked/unlinked job/submission and
  prepared-singleton production writers.
- Narrow source adapters to typed submission ports and receipts.
- Extend package/module checks with a focused kernel-bypass ratchet.
- Update architecture, daemon API, fleet operations, examples, and contributor
  documentation.

**Acceptance & Validation:**

- Every production submission enters through one application boundary.
- Surface modules cannot access the concrete Postgres submission writer.
- Pull scheduling and coordination remain separately owned interfaces.
- Checks fail on a reintroduced bypass.

### Phase 6: Regression and Cutover Validation

**Goal:** Prove the kernel replaces current writers safely.

**Scope:**

- Exercise benchmark multi-spec/repetition, build-only, validation, recovery,
  replay, assignment, terminal history, and reporting.
- Test fresh schema and upgrade from v27.1.
- Document deployment, backup verification, inspection, and rollback.
- Run full workspace validation.

**Acceptance & Validation:**

- Data/identity/audit checks match before/after the v27.2 migration.
- Constraints and assignments reject contradictory states.
- Benchmark and validation canaries submit, schedule, execute, report, and
  reconcile through the same kernel.
- Restart after commit/before acknowledgement returns the original receipt.
- No old writer remains callable in production.

  multi-orchestrator HA.

## Rollout and Rollback

Deploy only after v27.1 is running. Drain workers, stop daemon writers, verify a
restorable backup, apply the v27.2 migration, deploy the matching daemon/CLI,
validate idempotent submission without workers, then canary benchmark and
validation workers before resuming producers.

Rollback stops v27.2 writers/workers, restores the v27.1 database backup,
deploys v27.1 binaries, validates schema/version agreement, and resumes. No
mixed-version dual-write period is supported.
